## 本期三个核心概念

1. **持久队友** — team member 的 messages 跨唤醒保持,不像 subagent 每次 dispatch 全新。前端第二次被唤醒时,还记得第一次做了什么
2. **inbox 消息系统** — 每个队友有 inbox(消息队列),队友之间异步通信。前端给后端的 inbox 发消息,后端下次被唤醒时自动看到,读后清空
3. **消息广播** — broadcast_message 一次性给所有队友的 inbox 发消息。一条"需求变更"通知所有人收到

## Team Member 的三层架构

```
┌───────────────────────────────────────────────────┐
│  ① 持久上下文层(累积)                             │
│  config["messages"] 跨唤醒保持                    │
│  第一次: [system, user(task1)]                    │
│  第二次: [system, user(task1), asst, user(task2)]│
│  防止: 队友"忘记"之前做了什么(上下文累积)        │
├───────────────────────────────────────────────────┤
│  ② inbox 注入层(通信)                            │
│  if config["inbox"]:                              │
│    task = task + inbox 消息拼装                   │
│    config["inbox"].clear()                        │
│  防止: 队友之间无法传话(异步通信)                │
├───────────────────────────────────────────────────┤
│  ③ 队友工具循环(第 05 期复用,加通信工具)         │
│  while True: LLM → 看受限工具 → 决定调什么         │
│  和主循环结构完全一样,但 messages 持久 + tools 含通信│
└───────────────────────────────────────────────────┘
```

| 层 | 职责 | 能做到 | 做不到 |
|---|---|---|---|
| 持久上下文 | 上下文累积 | 让队友"记得"之前做了什么 | 自动总结历史(需 compact) |
| inbox 注入 | 异步通信 | 队友之间传话,唤醒时自动读取 | 消息持久化(程序退出后丢失) |
| 工具循环 | 驱动交互 | 队友自主完成多步任务 | 调用未授权工具 |

> Team Member 的 messages 是持久的(存在 TEAM_MEMBERS 注册表里),而 Subagent 的 sub_messages 是临时的(函数局部变量,函数结束即销毁)。

## 五个新工具

```python
# ① 唤醒持久队友(上下文跨唤醒保持,inbox 自动注入)
team_wake(member_id="frontend_dev", task="设计登录页面的 HTML 结构")
# → {member_id, wake_count, result, prompt_tokens, completion_tokens, elapsed_seconds}

# ② 给指定队友的 inbox 发消息(主 Agent 或队友都能调)
send_message(to_member="backend_dev", content="我需要登录接口的请求和响应格式")
# → {sent, from, to, content, inbox_size}

# ③ 向所有队友的 inbox 广播一条消息
broadcast_message(content="需求变更:登录功能需要增加验证码校验")
# → {broadcast, from, delivered_to, content}

# ④ 读取某个队友的 inbox(不消费,仅查看)
read_inbox(member_id="frontend_dev")
# → {member_id, unread_count, messages}

# ⑤ 查看团队成员列表及状态
list_team()
# → {members: [{member_id, description, inbox_unread, wake_count, has_context}, ...]}
```

> 五个工具和第 05-09 期的工具完全平等——加能力 = 加工具,核心循环一行没改。

## Subagent vs Team Member:完整对比

| 维度 | Subagent(第 09 期) | Team Member(本期) |
|---|---|---|
| 生命周期 | 临时:派遣→运行→销毁 | 持久:注册一次,可多次唤醒 |
| messages 位置 | 函数局部变量 | TEAM_MEMBERS 注册表(全局) |
| messages 持久性 | 每次全新 | 跨唤醒累积 |
| 通信方式 | 单向(结果回传) | 双向(inbox 异步消息) |
| 消息队列 | 无 | inbox(读后清空) |
| 并发支持 | ThreadPoolExecutor 真并发 | 串行唤醒(每次一个) |
| 唤醒计数 | 无 | wake_count |
| 工具白名单 | 3个(基础工具) | 5个(基础 + 通信) |
| 适用场景 | 独立任务(审查代码) | 多轮协作(前端+后端) |

## inbox 异步通信流程

```
时间线:
  t=0   前端被唤醒,需要后端接口
        → send_message(to_member="backend_dev", content="我需要登录接口格式")
        → backend_dev.inbox += 1条消息

  t=5   后端被唤醒
        → inbox 消息注入到 task:"--- 收到的队友消息 --- [frontend_dev] ..."
        → inbox 清空(已消费)
        → 后端设计接口,send_message 回复前端
        → frontend_dev.inbox += 1条消息

  t=10  前端再次被唤醒
        → inbox 消息注入:"--- 收到的队友消息 --- [backend_dev] 接口定义:..."
        → 前端看到后端回复,继续对接 API
```

> inbox 的核心设计:读后清空(唤醒时注入后立即 clear),不会重复消费。read_inbox 可查看但不消费。
