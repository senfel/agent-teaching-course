## 本期三大知识点

1. **Web UI(FastAPI + 内嵌前端)** — 给 14 期能力包一层 Web 外壳。六端点:`/health` 健康检查、`/goal` 读目标状态、`/sessions` 会话列表、`/history/{id}` 回放续聊、`/` 内嵌 HTML、`/chat` 对话(SSE)。入口双轨:`python -m step15_deploy`(Web)/ `--cli`(命令行),两者共用同一条 `build_system_prompt()` + `stream_chat_with_tools()`
2. **流式响应(SSE)** — LLM 调用 `llm_call_stream`(`stream=True` + `stream_options.include_usage`),`stream.py` 把增量文本/工具状态逐个 `yield` 成事件,Web 用 `StreamingResponse(media_type="text/event-stream")` 推给浏览器,前端 `fetch` + `getReader()` 逐块读。选 SSE 不选 WebSocket:聊天是"单向流 + 每轮结束",SSE 最小够用
3. **Docker 部署** — Dockerfile 分层缓存(依赖层最前,改代码只重建最后一层)+ docker-compose(env 注入 API Key、memory 挂卷持久化)+ .dockerignore 挡敏感文件

## 流式工具循环:与非流式是孪生

```python
# 规则:opentool_calls 的 id/name/arguments 是分片到达,按 index 攒,别漏别错位
while True:
    content_parts, tool_calls = [], {}          # index → {id,name,arguments}
    for delta, model_id in llm_call_stream(messages, tools=TOOLS):
        if delta.content:                       # 文本增量 → 立刻 yield
            yield {"event": "delta", "text": delta.content, "model": model_id}
        for tc in (delta.tool_calls or []):     # 工具调用分片 → 按 index 累加
            s = tool_calls.setdefault(tc.index, {"id":"","name":"","arguments":""})
            s["id"] = s["id"] or tc.id
            s["name"] += tc.function.name
            s["arguments"] += tc.function.arguments
    if not tool_calls:
        yield {"event": "done", "text": "".join(content_parts).strip()}; return
    for slot in sorted_by_index(tool_calls):    # 攒齐 → 执行工具 → 回灌 → continue
        yield {"event": "tool_call", ...}; result = _run_one_tool(...)
        yield {"event": "tool_result", ...}
```

> 与非流式 `chat_with_tools` 唯一区别:文本从"攒整段一次性返回"变成"逐增量 yield",工具状态从"print"变成"yield 事件"。循环结构、Hooks、路由记账完全一致。

## SSE vs WebSocket(为什么选 SSE)

| | SSE | WebSocket |
|---|---|---|
| 方向 | 单向(服务端 → 客户端) | 双向 |
| 协议 | 纯 HTTP,`text/event-stream` | 升级长连接 |
| 浏览器读法 | `EventSource` / `fetch` 流式读 | 需 WebSocket API |
| 适用 | 单向持续推(打字机、日志) | 双向实时(游戏、聊天室) |
| 本期结论 | ✅ 聊天=发一条、连续吐多个事件,SSE 最小够用 | 用不上双向,反而重 |

## 事件协议(stream.py 的 yield 契约)

| event | 字段 | 前端渲染 |
|---|---|---|
| `delta` | `{text, model}` | 追加到当前气泡(逐字) |
| `tool_call` | `{name, arguments}` | "🔧 调用工具: xxx" |
| `tool_result` | `{name, result}` | "✅ xxx 完成: …" |
| `done` | `{text}` | 收尾,清空当前气泡 |
| `error` | `{message}` | "⚠️ 出错: …" |

## 会话列表与历史回放(事件溯源的直接产品)

Web 层不需要单独建"会话表"—— 直接扫 `memory/raw_history.jsonl`(前 7 期开始攒的那份 append-only 原始历史),按 `session` 字段聚合即得会话列表:

| 端点 | 作用 |
|---|---|
| `GET /sessions` | 聚合所有历史会话(id / 条数 / 首末时间 / 最后一条消息 / 标题),左侧栏渲染 |
| `GET /history/{session_id}` | 回放该会话的 user/assistant,并调 `_ensure_session` 重建成进程内上下文 |

`_ensure_session` 负责"续聊":首次或服务重启后,从落盘历史把 user/assistant 回放进 messages,前端就能接着上次聊。一个教训:Web 是"无状态 HTTP",但 Alex 是"有状态 Agent" —— 光靠进程内 `_SESSIONS` 存上下文不够(重启就丢),必须回放 raw_history 兜底(生产版换 Redis/数据库,衔接方式不变)。
