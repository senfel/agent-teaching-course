## 本期三个核心概念

1. **独立上下文** — 子代理有自己的 messages(全新,不复用主 Agent 对话历史),审查和整理互不污染
2. **工具白名单** — 从 11 个工具中过滤出 allowed 的 3 个,LLM 看不到其他 8 个 = 物理隔离,不是"提醒"
3. **并发派遣** — ThreadPoolExecutor 真并发,总耗时 ≈ max(各子代理),不是 sum

## 子代理的三层架构

```
┌───────────────────────────────────────────────────┐
│  ① 独立上下文层(隔离)                            │
│  sub_messages = [system + extra_prompt, task]     │
│  不复用主 Agent 对话历史                           │
│  防止:子任务互相污染(审查的细节混进整理思路)     │
├───────────────────────────────────────────────────┤
│  ② 工具白名单层(权限)                            │
│  sub_tools = [t for t in TOOLS if name in allowed]│
│  从 11 个工具中过滤出 3 个,LLM 看不到其他 8 个    │
│  防止:子代理调 todo/save_profile/dispatch(越权)  │
├───────────────────────────────────────────────────┤
│  ③ 子代理工具循环(第 05 期复用)                   │
│  while True: LLM → 看受限工具 → 决定调什么         │
│  和主循环结构完全一样,只是 messages + tools 不同   │
└───────────────────────────────────────────────────┘
```

| 层 | 职责 | 能做到 | 做不到 |
|---|---|---|---|
| 独立上下文 | 上下文隔离 | 防止子任务互相污染 | 子代理"记住"主 Agent 背景 |
| 工具白名单 | 权限控制 | 阻止调用未授权工具 | 阻止 prompt 里"提到"工具名 |
| 工具循环 | 驱动交互 | 子代理自主完成多步任务 | — |

> 工具白名单是"物理隔离":子代理的 LLM 根本不知道 dispatch_subagent 的存在,不是"知道但被提醒不要用"。

## 三个新工具

```python
# ① 派遣单个子代理(同步,阻塞直到完成)
dispatch_subagent(agent_type="code_reviewer", task="审查这段代码:...")
# → {agent_type, result, prompt_tokens, completion_tokens, elapsed_seconds}

# ② 并发派遣多个子代理(真并发,总耗时 ≈ max)
dispatch_subagents_parallel(tasks=[
    {"agent_type": "code_reviewer", "task": "审查代码:..."},
    {"agent_type": "doc_writer", "task": "整理文档:..."},
])
# → {dispatched: 2, elapsed_seconds: 10.5, results: [...]}

# ③ 查看可用子代理类型及权限
list_subagents()
# → {available: [{type, description, allowed_tools}, ...]}
```

> 三个工具和第 05-08 期的工具完全平等——加能力 = 加工具,核心循环一行没改。

## 工具白名单:物理隔离 vs 提醒

| 方式 | 实现 | LLM 能看到未授权工具吗 | 能调用吗 |
|---|---|---|---|
| 提醒式(错误) | prompt 里写"不要用 dispatch_subagent" | 能看到 | 能调用(只是可能不调用) |
| 白名单(正确) | 从 TOOLS 列表过滤掉 | 看不到 | 调不了(工具不存在) |

子代理权限设计:
- 允许:`get_current_time`、`calculate`、`load_skill`(3 个)
- 禁止:`todo_*`(只有主 Agent 管任务)、`save_user_profile`/`recall_memory`(只有主 Agent 管记忆)、`dispatch_*`(禁止递归派遣)

## 串行 vs 并发:时间对比

```
串行派遣:
  t=0s   ──── 代码审查(10s) ────┐
  t=10s                            ├── 文档整理(8s) → 总 18s

并发派遣:
  t=0s   ──── 代码审查(10s) ────┐
  t=0s   ── 文档整理(8s) ──┐    │
  t=8s                       │    │
  t=10s                            ┘ → 总 10s = max(10, 8)
```

> DeepSeek API 调用是 I/O 密集型,Python GIL 在 I/O 等待时释放,线程级并发能真正加速。
