CONCEPT
02 / 10

单模型写死 vs 多模型路由 —— 从"一个大脑"到"调度台"

🧠 单模型写死(第 12 期)

每次调用都写死 model=MODEL
查时间和做架构评审,用同一个模型

简单任务也在烧旗舰的钱

月底看账单:只知道花了多少,不知道花在哪、值不值

🛫 多模型路由(本期)

调用前先问路由器:这活儿该给谁?
简单 → light 档,复杂 → heavy 档,后台 → 永远便宜档

调用后记账:token × 单价 → usage_log.jsonl

运行实测:12 次调用 $0.037,若全用 claude-sonnet 要 $0.269 —— 省 86%

路由 = 在"调用"和"模型"之间加一个决策层;telemetry = 给每次调用装一个计价器

类比出租车调度:接个机就用经济型,跑长途商务就上商务舱。车队(模型池)在注册表里,派单规则(路由策略)在路由器里,谁跑了多少公里花了多少钱(成本)在台账里。

路由路径什么时候走结果
auto · 规则命中复杂关键词(审查/分析/设计…)或消息超 400 字符heavy 档(deepseek-reasoner)
auto · 默认简单任务:无关键词、消息不长light 档(deepseek-chat)
backgroundcompact 压缩 / 子代理 / 队友调用固定 light 档(省钱策略)
manual用户 switch_model 钉住某模型钉住的模型,直到切回 auto

单价不是写死的数字,而是 MODEL_REGISTRY 注册表里的字段——换模型、调价格,只改注册表;路由规则和记账公式一行不动。

STEPS
05 / 10

三层结构 + 三个新工具

  1. 注册表层 — MODEL_REGISTRY:每个模型的档位/单价/强项/api_model;4 个模型进池子(light×2 + heavy×2)
  2. 路由层 — route_model / resolve_model:关键词 + 长度规则自动选档;manual 钉住优先;后台任务固定 light 档
  3. 挂载点 — llm_call:全部 LLM 调用的唯一入口,路由在前、记账在后;main/compact/subagent/team 四处调用点全部收编
新工具(22 → 25)作用
list_models查看模型池:档位、单价、强项 + 当前路由模式
switch_modelauto/manual 切换;manual 需给 model_id(还能附任务说明)
cost_report成本报表:各模型 token 用量与美元花费

为什么 LLM 自己需要这些工具?当用户说"这题用强模型做"时,Alex 能自己调 switch_model 钉住旗舰档——模型选择从"用户配置"升级成"Agent 可操作的技能"。

CODE
07 / 10

核心代码 · llm_call 统一入口

def llm_call(messages, task="main", tools=None, max_tokens=4096):
    # ① 路由:决定这次调用用哪个模型
    model_id, reason = resolve_model(messages, task=task)   # manual钉住 > 后台light > auto规则
    _record_route(model_id, reason, task)                     # 打印 + 路由历史
    api_model = MODEL_REGISTRY[model_id]["api_model"]         # 逻辑名 → 真实端点名

    # ② 调用:按注册表映射发往真实端点
    kwargs = {"model": api_model, "messages": messages, "max_tokens": max_tokens}
    if tools:
        kwargs["tools"] = tools; kwargs["tool_choice"] = "auto"
    response = client.chat.completions.create(**kwargs)

    # ③ 记账:成本 telemetry(token × 单价 → 美元)
    log_usage(model_id, response.usage.prompt_tokens,
              response.usage.completion_tokens, task)          # → usage_log.jsonl
    return response, model_id

第 12 期四处直接调 client.chat.completions.create(model=MODEL) 的地方(main 工具循环 / compact 压缩 / 子代理 / 队友),本期全部改成 llm_call——一处收编,处处路由。

教学环境只有一个 DeepSeek key:claude-sonnet / local-qwen 用 DeepSeek 端点"模拟"——路由和计费机制与生产完全一致。生产接入真实供应商只改注册表和 base_url,主逻辑零改动,这就是"路由层抽象供应商差异"。

WHY
08 / 10

为什么 Agent 需要多模型路由?

😖 没有路由(一个大脑)

查时间也用旗舰模型 → 按 token 白烧钱

compact/子代理/队友全走同一个贵模型

想换供应商 → 满屏 model=XXX 到处改

月底账单一笔总账,看不出哪个任务在吃钱

😌 有路由(调度台)

简单任务走 light 档,后台任务永远 light 档

换供应商 = 注册表加一行 + 改一个 base_url

钉住/自动切换,是 Agent 可自调用的工具

usage_log.jsonl 按模型/任务记账,花在哪一目了然

前 12 期管"能力和约束",本期管"经济账"——生产 Agent 的成本分水岭。

Telemetry 的意义不只是省钱:知道每个任务类型烧多少 token,才知道该给哪类任务配什么档——"省 86%"是路由策略带来的,但结论是数据告诉你的。
