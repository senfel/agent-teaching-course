第 01 期你跑通了第一次调用。但只要多问两句,它就露馅了——
前脚告诉它"我叫张三",后脚问"我姓什么",它答不上来。

DEMO
02 / 10

循环有了 · 记忆没来

你: 我叫张三,是一名 Python 后端工程师
Alex: 你好,张三!很高兴认识你……
你: 我姓什么?我是做什么工作的?
Alex: 抱歉,我不知道你姓什么,也没法知道你的职业……
↑ 上一句刚说,这一句就忘了

明明上一句刚说过,下一句就忘了

这不是 DeepSeek 的毛病,OpenAI、Claude、Gemini 都一样。原因在下一页:API 是无状态的。

FORMULA
03 / 10

真相:API 是无状态的

请求 A
"我叫张三"
≠
请求 B
"我姓什么"

服务器把 每一次 请求当成全新对话

模型不记得上一句,是因为你根本没把上一句发给它。"连续对话"是客户端伪造出来的幻觉——你维护一份历史,每次一起发过去,下一期就这么做。

STEPS
05 / 10

本期 3 个动作

  1. while 循环 — 把"一问一答"串成连续对话的形式
  2. 故意不传 history — messages 里永远只有当前一句,暴露金鱼记忆
  3. token 计数可视化 — 读 response.usage,看到上下文是空的

第 3 步是关键伏笔:你会发现每次调用的 prompt_tokens 都很小(就一句话)。下一期加上 history 后,这个数字会越滚越大——那就是上下文长度问题的由来。

CODE
07 / 10

核心代码 · 只传当前一句

def chat(user_input: str) -> tuple[str, int, int]:
    response = client.chat.completions.create(
        model=MODEL,
        messages=[{"role": "user", "content": user_input}],  # ← 只有这一句
        max_tokens=1000,
    )
    answer = response.choices[0].message.content
    usage = response.usage
    return answer, usage.prompt_tokens, usage.completion_tokens

关键:messages 里永远只有当前这一句,模型看不到上一句——这就是金鱼记忆的代码真相。

下一期只需要在这里动刀:把 messages 换成一份历史列表,每次回灌进去,模型就"记得"了。

为什么加 token 可视化?

📊 看见上下文是空的

prompt_tokens(输入) · completion_tokens(输出) · total_tokens(合计)

TRY IT
09 / 10

试一试 · 4 个伏笔

  • 复本金鱼记忆 — 先说"我叫张三",再问"我姓什么"
    亲眼看到它答不上来,比读十句概念都管用
  • 观察 prompt_tokens — 每次调用的 prompt 是多少?为什么这么小?
    下期加 history 后再回来对比,你会恍然大悟
  • 输入 reset — 程序会提示"本期尚未实现记忆"
    这行代码是故意留的伏笔,第 03 期会真正实现它
  • 思考题 — 想让模型记住上一句,最朴素的办法是?
    答案就是下一期:把上一轮问答塞进 messages 一起发过去

💡 学完这一期,你应该能跑通循环对话,并理解"金鱼记忆"是 API 无状态导致的,不是模型笨。
