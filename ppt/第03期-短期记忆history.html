同样两个问题 · 这次记住了

你: 我叫张三,是一名 Python 后端工程师
Alex: 你好,张三!
你: 我姓什么?我是做什么工作的?

↑ 这次答上来了 — 因为 messages 里带着上一轮的问答

把完整对话历史塞进 messages,模型就"记住"了

模型本身还是无状态的,但你每次把历史一起发过去,它就能"看到"上下文。

STEPS
05 / 10

本期 3 个动作

  1. 维护 messages 列表 — 每轮把 user + assistant 都加进去
  2. 回灌历史调用 API — 传完整 messages,模型就能看到上下文
  3. 超 10 轮截断最早 — 简单截断,防止历史无限膨胀

第 1 步是核心:把模型回复也加回 messages,下一轮调用时它就"记住"了。第 3 步是边界处理——历史越多 token 越贵,也越容易触顶。

CODE
07 / 10

核心代码 · 回灌历史

# 维护 messages 列表
messages: list[dict] = []

# 用户输入加入历史
messages.append({"role": "user", "content": user_input})

# 调用 API — 传完整 messages(不再只传当前一句)
answer, p, c = chat(messages)

# 模型回复也加回历史 ← 关键!
messages.append({"role": "assistant", "content": answer})

关键:把模型回复也加入 messages,下一轮调用时它就"记住"了。

对比第 02 期:chat() 入参从"一句话 str"变成"完整 messages 列表"。

WHY
08 / 10

token 增长 · 看见上下文

轮次第 02 期 prompt_tokens第 03 期 prompt_tokens
第 1 轮~10(一句话)~10(一句话)
第 2 轮~10(还是一句话)~30(含第 1 轮问答)
第 5 轮~10~150(含前 4 轮)

历史越多,token 越贵,也越容易触顶

这就是上下文长度问题的由来 — 第 07 期会用 compact 压缩解决

TRY IT
09 / 10

试一试 · 5 个动手实验

  • 对比第 02 期 — 先说"我叫张三,后端工程师",再问"我姓什么"
    这次模型应该能答上来
  • 观察 prompt_tokens 增长 — 多聊几轮,看 prompt 是不是越来越大?
    这就是上下文在增长
  • 输入 history — 打印当前 messages 列表
    直观看到 [user, assistant, user, assistant, ...] 的结构
  • 超过 10 轮 — 故意聊超过 10 轮,输入 history 看最早的是否被截断
    简单截断策略的效果
  • 思考题 — 直接删掉最早一轮会丢失重要信息,有没有更好的办法?
    答案就是第 07 期的 compact 压缩

💡 学完这一期,你应该能用 messages 列表让模型"记住"对话,并理解 token 增长和上下文限制。
