STRUCTURE
05 / 11

SKILL.md · frontmatter + 正文

---
name: git-cheatsheet
description: Git 命令速查。当用户问
  "怎么撤销提交""怎么回退版本"
  等问题时使用。
---

# Git 速查(正文,给模型看)

| 场景 | 命令 |
|---|---|
| 撤销提交(保留修改) | reset --soft HEAD~1 |
| 回退版本 | reset --hard <commit>

两个必填字段

  • name — 技能名,与目录名一致(load_skill 按目录查找)
  • description — 什么时候用,模型的路由依据

本期两个示例技能

weather流程型:流程 + 模拟规则 + 模板 + 边界
git-cheatsheet知识型:速查表本身,加载即答案

frontmatter 只需 name + description 两个字段——解析都不用 pyyaml,按行 partition(":") 就够。git-cheatsheet 是学员亲手写的第一个技能。

CORE
06 / 11

两级加载 · 索引常驻,全文按需

启动时(第一级): 扫描 skills/*/SKILL.md → 只解析 frontmatter → 索引追加到 system prompt 尾部
system: "你是 Alex..." + "可用技能: weather(查天气...) / git-cheatsheet(Git 问题...)" ← 索引几百字,常驻

user: "Git 怎么撤销上次提交?"
assistant: tool_calls=[load_skill(name="git-cheatsheet")] ← 模型看索引,自己决定
↓ 执行: 读 skills/git-cheatsheet/SKILL.md 全文
tool: {"skill": "git-cheatsheet", "content": "# Git 速查..."} ← 全文注入,只在本轮
assistant: "用 git reset --soft HEAD~1,撤销提交但保留修改……" ← 按手册回答

关键:load_skill 就是一个普通工具,完全复用第 05 期的工具循环——工具循环一行代码没改。

技能全文进的是 tool 消息,随历史回灌;超轮截断后模型需要时会再调一次 load_skill,天然自愈。

CODE
07 / 11

核心代码 · 索引 + load_skill

第一级:扫索引

def load_skills_index():
    index = []
    for d in sorted(SKILLS_DIR.iterdir()):
        f = d / "SKILL.md"
        meta = parse_frontmatter(
            f.read_text(encoding="utf-8"))
        if not meta.get("name"):
            continue  # 不算技能
        index.append({
            "name": meta["name"],
            "description": meta.get("description", ""),
        })  # ← 只留两个短字段
    return index

第二级:按需取全文

if name == "load_skill":
    skill_md = SKILLS_DIR / arguments["name"] \
               / "SKILL.md"
    return json.dumps({
        "skill": arguments["name"],
        "content":
            skill_md.read_text("utf-8"),
    }, ensure_ascii=False)
    # 全文此刻才进上下文
    # 没用到的技能 = 0 token

system prompt 组装 = SOUL.md 人设 + build_skills_prompt(index)。命令行新增 skills:随时查看索引。

WHY
08 / 11

为什么"索引 + 按需"是对的模式?

方案2 个技能20 个技能200 个技能
全量塞 system prompt ~1K token ~10K token 爆上下文
Skills 两级加载 索引 ~100 索引 ~500 索引 ~4K,仍可运行

全量方案的问题

  • 成本随技能数线性增长
  • 每轮都付,90% 的对话用不上

Skills 方案的账

  • 常驻只付索引的钱
  • 全文只在用到的轮次付一次

这也回答了"为什么 description 要写'什么时候用'"——它是路由器,写歪了模型就会加载错技能。

DESIGN
09 / 11

SKILL.md 设计三原则

  1. description 写"什么时候用",不是"这是什么"
    "Git 命令速查" ✗ → "当用户问怎么撤销提交、回退版本时使用" ✓ ——模型靠它路由
  2. 正文写给模型看,不是写给人看
    多用表格和步骤,少用散文——模型照着执行,冗余文字只是浪费 token
  3. 写清边界
    "不编造精确到小时的预报"这类约束句,是防止技能被滥用的小保险

💡 一种技能一个目录,目录名 = name。加技能 = 加目录,代码零改动——这就是"技能库"的可扩展性。

这也正是 Trae / Claude Code 等真实 Agent 产品的 Skills 机制原型:frontmatter 索引 + 按需注入,生产环境同款思路。

试一试 · 6 个动手实验

  • 看自动演示 — 启动后问"Git 怎么撤销上次提交?"

    看模型路由到 weather 技能,按模板回答并注明"模拟数据"
  • 输入 skills — 打印技能索引
    直观对比"索引几十字"和"全文几千字"的差距
  • 连续追问 — 再问"那已经 push 了怎么办?"
    观察模型不再调 load_skill——历史里已有全文,省一次加载
  • 自己写一个技能 — 新建 skills/python-review/SKILL.md
    frontmatter 写清 description,正文放代码评审 checklist,写完输入 skills 确认被识别
  • 思考题 — 技能结果如果写进 system prompt 会怎样?
    提示:trim_history 永远保留 system,技能全文会永久占上下文——正是两级加载要避免的
