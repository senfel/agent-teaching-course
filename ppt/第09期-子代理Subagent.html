CONCEPT
02 / 10

串行排队 vs 并发派遣

🐌 串行(第 08 期)

"审查代码 + 整理文档" → 先审查,做完了再整理

上下文共享:审查的细节污染整理思路

总耗时 = sum:10s + 8s = 18s

类比:一个人干两件事,排队来

🔀 并发(第 09 期)

"审查代码 + 整理文档" → 两个子代理同时跑

上下文隔离:各自干净,互不干扰

总耗时 = max:max(10s, 8s) = 10s

类比:派两个专家同时干活

给 Agent 加 分身能力

第 08 期的 TodoList 是"任务记忆"(把做什么从隐式变显式),第 09 期的子代理是"分身能力"(把"一个人干"变成"派活给专家")。

设计思路和前面几期一脉相承——07 期把"用户是谁"从 messages 搬到 USER.md,08 期把"我在做什么"搬到 _todo_list,09 期把"谁来做"拆成独立子代理。都是"隐式→显式""单体→分治"。

⚠ 工具白名单 = 物理隔离:不是在 prompt 里说"不要用某某工具",而是直接从 TOOLS 列表里删掉。LLM 根本看不到未授权工具,不是"提醒"。

WORKFLOW
05 / 10

子代理派遣流程 · 5 步

  1. 判断是否需要子代理 — 任务涉及多个专家角色(如代码审查 + 文档整理)时,用 dispatch_subagents_parallel
  2. 创建子代理上下文 — 全新 messages = [system + extra_prompt, task],不复用主 Agent 对话历史
  3. 应用工具白名单 — 从 11 个工具中过滤出 allowed 的 3 个,LLM 看不到其他 8 个
  4. 子代理自主执行 — 自己的 while True 工具循环,独立调工具、看结果、做决策
  5. 结果回传主 Agent — 子代理返回最终文本,主 Agent 汇总后回复用户

注入到 system prompt 的"子代理使用指南"(内联),核心原则:多专家用并发,单专家用单独派遣,不确定有哪些子代理用 list_subagents 查看。

关键:子代理的对话过程不会出现在主 Agent 的上下文里。主 Agent 只收到子代理的最终结果文本,不是它们的对话过程。这就是"独立上下文"——子代理干活时,主 Agent 的脑子不被污染。

核心代码:子代理 + 并发派遣

# ① 独立上下文 + 工具白名单
def _run_subagent(agent_type: str, task: str):
    config = SUBAGENT_TYPES[agent_type]
    # ① 独立上下文:全新 messages
    sub_messages = [{"role": "system", "content": sub_system},
                    {"role": "user", "content": task}]
    # ② 工具白名单:从 11 个工具中过滤出 allowed 的
    allowed = set(config["allowed_tools"])
    sub_tools = [t for t in TOOLS if t["function"]["name"] in allowed]
    # ③ 子代理自己的工具循环
    while True:
        response = client.chat.completions.create(
            messages=sub_messages, tools=sub_tools, ...)
        # ... 工具调用处理,和主循环一样 ...

# ② 并发派遣:ThreadPoolExecutor 真并发
def dispatch_subagents_parallel(tasks: list[dict]):
    with ThreadPoolExecutor(max_workers=n) as executor:
        futures = {}
        for i, t in enumerate(tasks):
            future = executor.submit(_run_subagent, t["agent_type"], t["task"])
            futures[future] = i
        for future in as_completed(futures):
            result, p, c = future.result()
            results[futures[future]] = {"result": result, ...}
    # 总耗时 ≈ max(各子代理耗时),不是 sum

子代理的工具循环和主循环结构完全一样(都是 while True),只是 messages 和 tools 不同。这是累积式的体现:第 05 期建的工具循环,主 Agent 用,子代理也用,核心结构一行没改。

注意工具白名单的实现——不是"标记"哪些工具可用,是直接从 TOOLS 列表过滤出一个新的 sub_tools 列表传给 LLM。LLM 的 API 调用里只有 3 个工具定义,它根本不知道另外 8 个存在。这就是"物理隔离"和"提醒"的区别。

HOW IT WORKS
08 / 10

多角色 Prompt vs 子代理

🎭 多角色 Prompt(一个 Agent 扮演多个角色)

上下文 共享,互相干扰

工具 全部可用,无权限控制

执行 串行,一个角色做完换下一个

token 越堆越长

类比:一个人同时演两个角色

🔀 子代理(本期)

上下文 独立,互不干扰

工具 白名单,物理隔离

执行 可并发,ThreadPoolExecutor

token 固定,每个子代理独立

类比:派多个专家各自干活

把"一个超级 Agent 扮演所有角色"拆成"多个专家 Agent 各司其职"

串行 vs 并发的时间差异:串行总耗时 = sum(各子代理耗时),并发总耗时 = max(各子代理耗时)。DeepSeek API 调用是 I/O 密集型,Python GIL 在 I/O 等待时释放,所以线程级并发能真正加速。

关键洞察:子代理把"一个超级 Agent 扮演所有角色"拆成"多个专家 Agent 各司其职"。这和第 07 期把"对话记忆"拆成"长期记忆 + 会话记忆"是同一个设计思路——分而治之。

    子代理无法调用 todo_create——它根本看不到这个工具(物理隔离)
