15 期系列 · 第 10 期 · 2026

上一期 Alex 有了"临时分身"——子代理用完即弃。
这一期给它"持久团队"——队友有记忆、有 inbox、能互相传话,真正模拟"前端组+后端组"协作开发。

PROBLEM
02 / 10

子代理是"临时工" —— 用完即弃

⚠ 子代理做不到

无持久状态 — 每次 dispatch 全新 messages,上次做了什么全忘了

单向通信 — 只能把结果返回给主 Agent,不能给其他子代理发消息

无消息队列 — 没有 inbox,队友之间无法异步传话

💡 需要什么?

持久队友 — messages 跨唤醒保持

inbox 消息 — 队友之间异步传话

消息广播 — 一条通知所有人收到

让前端给后端发消息"我需要接口格式"
后端下次被唤醒时自动看到 —— 这就是 Agent Team

子代理是"临时工"(派遣→运行→结果→销毁),团队成员是"持久队友"(注册→可多次唤醒→上下文累积)。

COMPARE
04 / 10

Subagent vs Team Member

维度Subagent(第 09 期)Team Member(本期)
生命周期临时:派遣→运行→销毁持久:注册一次,可多次唤醒
messages函数局部变量,每次全新注册表全局,跨唤醒累积
第二次唤醒全新上下文,不记得上次看到第一次的对话,上下文累积
通信单向(主→子→结果回传)双向(inbox 异步消息)
消息队列无inbox(读后清空)
工具白名单3 个(基础工具)5 个(基础 + 通信工具)
适用场景独立任务(审查代码)多轮协作(前端+后端开发)

关键:Subagent 的 sub_messages 是函数局部变量(函数结束即销毁),Team Member 的 messages 存在 TEAM_MEMBERS 注册表里(全局持久)。这是持久队友和临时子代理的本质区别。

INBOX
05 / 10

inbox 异步通信 —— 队友怎么传话

t=0   前端被唤醒,需要后端接口

   → 调 send_message(to_member="backend_dev", content="我需要登录接口格式")

   → backend_dev 的 inbox += 1 条消息

▼

t=5   后端被唤醒

   → inbox 消息自动注入到 task:"--- 收到的队友消息 --- [frontend_dev] 我需要登录接口格式"

   → inbox 清空(已消费)   → 后端设计接口,回复前端

   → frontend_dev 的 inbox += 1 条消息

▼

t=10   前端再次被唤醒

   → inbox 消息注入:"[backend_dev] 接口定义: POST /api/login..."

   → 前端看到后端回复,继续对接 API

inbox 设计要点:读后清空(唤醒时注入后立即 clear,不会重复消费);read_inbox 可查看但不消费。

TOOLS
06 / 10

五个新工具(16 个 = 11 + 5)

# ① 唤醒持久队友(上下文跨唤醒保持,inbox 自动注入)
team_wake(member_id="frontend_dev", task="设计登录页面的 HTML 结构")

# ② 给指定队友的 inbox 发消息(主 Agent 或队友都能调)
send_message(to_member="backend_dev", content="我需要登录接口格式")

# ③ 向所有队友的 inbox 广播一条消息
broadcast_message(content="需求变更:增加验证码校验")

# ④ 读取某个队友的 inbox(不消费,仅查看)
read_inbox(member_id="frontend_dev")

# ⑤ 查看团队成员列表及状态
list_team()

五个工具和第 05-09 期的工具完全平等——加能力 = 加工具,核心循环一行没改。

累积式:step10 = step09 + Agent Team。子代理代码全部保留,只新增 Team 层 + 5 个工具。

ARCHITECTURE
07 / 10

Team Member 三层架构

① 持久上下文层(累积)

config["messages"] 跨唤醒保持

第一次: [system, user(task1)]

第二次: [system, user(task1), asst, user(task2)]

队友"记得"之前做了什么

② inbox 注入层(通信)

if config["inbox"]:

  task = task + inbox 消息拼装

  config["inbox"].clear()

唤醒时自动读取未读消息,读后清空

③ 队友工具循环(第 05 期复用,加通信工具)

while True: LLM → 看持久 messages + 受限工具 → 决定调什么

队友可调 send_message 给其他队友发消息

和主循环结构完全一样,但 messages 持久 + tools 含通信

Team Member 的 messages 存在 TEAM_MEMBERS 注册表(全局持久),Subagent 的 sub_messages 是函数局部变量(函数结束即销毁)。

DEMO
08 / 10

演示:前端+后端协作开发"用户登录功能"

# 用户: "让前端和后端协作开发登录功能"

# 1. 主 Agent 唤醒后端,设计登录接口
[工具调用] team_wake({'member_id': 'backend_dev', 'task': '设计登录接口'})
  [team·backend_dev] # 设计 POST /api/login 接口
  [team·backend_dev] send_message({'to_member': 'frontend_dev', ...})

# 2. 唤醒前端,设计登录页面
[工具调用] team_wake({'member_id': 'frontend_dev', 'task': '设计登录页面'})
  [team·frontend_dev] # 读取 1 条 inbox 消息 ← 看到后端的接口定义!
  [team·frontend_dev] # 根据后端接口设计页面
  [team·frontend_dev] send_message({'to_member': 'backend_dev', 'content': '验证码字段怎么传?'})

# 3. 再次唤醒后端(持久上下文!记得第一次设计了什么)
[工具调用] team_wake({'member_id': 'backend_dev', 'task': '回复前端问题'})
  [team·backend_dev] # 读取 1 条 inbox 消息 ← 看到前端的问题!
  [team·backend_dev] # 上下文中有第一次的对话记录 → 知道接口已有验证码字段
  [team·backend_dev] send_message({'to_member': 'frontend_dev', 'content': '验证码用 code 字段...'})

后端第二次被唤醒时,messages 里有第一次的对话记录——这就是持久上下文的意义。
