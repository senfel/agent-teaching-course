# 第 08 期:任务规划 TodoList

## 问题

第 07 期 Alex 有了记忆系统——跨会话也能记住你的偏好了。但面对复杂任务时,Alex 还是个"无头苍蝇"。

你说"帮我准备周会",Alex 直接一口气写完——不拆任务、不标进度、不勾完成。更糟的是,如果你让它同时做三件事,它"同时开三个头、一个没收尾",最后一个都没做完。

本质问题:Alex 缺少**任务规划能力**——不会把模糊需求拆成可执行子任务,不会用状态机管理进度,更不会约束自己"一次只做一件事"。

## 解决方案

### 1. TodoList 三状态机

引入一个简单的任务状态机,每个任务有三个状态:

```
pending → in_progress → completed
  ⬚        ▶            ✓
```

| 状态 | 含义 | 图标 |
|---|---|---|
| `pending` | 待办,还没开始 | ⬚ |
| `in_progress` | 正在做 | ▶ |
| `completed` | 已完成 | ✓ |

工作流:**创建全部 pending → 逐个推 in_progress → 做完标 completed → 下一个**。

### 2. 三个新工具

```python
# 创建任务列表(Agent 收到复杂任务时先调)
todo_create(tasks=["收集本周工作要点", "整理待讨论议题", "写周报草稿"])
# → 返回 [{id:1, content:"收集...", status:"pending"}, ...]

# 更新任务状态(开始做时调,双约束在这里执行)
todo_update(task_id=1, new_status="in_progress")
# → 顺序约束拦住"跳过",单 in_progress 拦住"并行"

# 查看进度
todo_list()
# → 返回 {total:3, pending:2, in_progress:1, completed:0, tasks:[...]}
```

这三个工具和第 05 期的 `get_current_time`、第 06 期的 `load_skill`、第 07 期的 `save_user_profile` **完全平等**——都走同一套工具循环。累积式的好处再次体现:加能力 = 加工具,核心循环不变。

### 3. 两条核心约束:顺序 + 单 in_progress

核心设计:**必须按顺序逐个推进,同一时刻只能有一个任务处于 in_progress**。

**约束 1(顺序):** 设为 `in_progress` 时,排在前面的任务必须全部 `completed`。不允许跳过 #1 直接开 #3。

```python
def todo_update(task_id, new_status):
    # 约束 1:顺序约束 —— 前面的任务必须全部完成
    if new_status == "in_progress":
        blocked_by = []
        for t in _todo_list:
            if t["id"] < task_id and t["status"] != "completed":
                blocked_by.append(t["id"])
        if blocked_by:
            return f"顺序约束:任务 #{task_id} 前面还有未完成任务 {blocked_by}"
```

**约束 2(单 in_progress):** 同一时刻只能有一个任务处于 `in_progress`。设新的会自动把旧的退回 `pending`。

```python
    # 约束 2:单 in_progress —— 把其他 in_progress 的退回 pending
    if new_status == "in_progress":
        for t in _todo_list:
            if t["status"] == "in_progress" and t["id"] != task_id:
                t["status"] = "pending"
    target["status"] = new_status
```

为什么需要这两条约束?

| 没有约束 | 只有单 in_progress | 顺序 + 单 in_progress |
|---|---|---|
| 同时开 5 个头,1 个没收尾 | 不同时开,但可以跳着做 | 必须一条条往下走 |
| 进度条乱跳 | 进度条不乱跳 | 进度条不乱跳 + 不跳过 |
| 用户不知道"做到哪了" | 知道哪个在做 | 知道哪个在做 + 下一个确定 |

两条约束共同强制 Agent:**一条条往下执行,不跳过、不并行**。这模拟了人类的工作习惯:一次专注一件事,做完一个再做下一个。

### 4. 纯内存设计:用完即弃

TodoList 存在运行时内存(`_todo_list` 变量)中,**不持久化到磁盘**。设计意图:

| 维度 | 内存变量(本期) | 持久化文件(未来进阶) |
|---|---|---|
| 程序关了 | 任务清空 | 跨会话保留 |
| 适用场景 | 单次任务执行 | 长期项目跟踪 |
| 复杂度 | 低,聚焦状态机逻辑 | 高,需要读写同步 |
| 本期定位 | 聚焦"规划→执行→勾选"核心闭环 | — |

全部任务完成后,列表自动清空,回到初始状态。本期聚焦于**状态机逻辑和双约束机制**,持久化是工程增强,留给后续进阶。

### 6. System Prompt 注入 TodoList 指南

在 system prompt 尾部追加一段 TodoList 工作指南(从 `templates/todo_guide.md` 加载),核心原则:**按任务列表执行,而不是随意回答**。

指南要求 Agent 每轮对话的决策流程:

1. 先调 `todo_list` 查看当前任务状态
2. 如果有 `in_progress` 的任务 → 用户输入视为该任务的补充信息 → 执行 → 标完成 → 开始下一个
3. 如果所有任务都 `completed` → 汇总所有步骤产出,输出最终交付物 → 列表自动清空
4. 如果列表为空 → 判断用户是否提出新复杂任务 → 是则调 `todo_create` 拆解

关键改进:旧指南只在"用户提出复杂任务时"触发。新指南明确**每轮对话先查 todo_list**,有 `in_progress` 任务就把用户输入当作该任务的补充信息,推进任务而不是闲聊。

## 工作原理

### TodoList 的三层架构:工具层 + 提示词层 + 工具循环

TodoList 不是单个组件,而是三层协作:

```
┌─────────────────────────────────────────────────────────┐
│  提示词层(软约束,引导行为)                             │
│  templates/todo_guide.md → 注入 system prompt            │
│  告诉 LLM:"每轮先查 todo_list,有 in_progress 就推进,   │
│           需要用户信息就停下,不要自己编"                 │
│  特点:模型可能不遵守(软约束),但 99% 会跟随            │
├─────────────────────────────────────────────────────────┤
│  工具层(硬约束,强制执行)                               │
│  todo_create / todo_update / todo_list 三个 Python 函数  │
│  双约束在这里硬编码:                                    │
│    约束 1(顺序):跳过 → 返回错误                       │
│    约束 2(单 in_progress):设新的 → 旧的自动退回        │
│  特点:模型无法绕过(硬约束),工具直接拒绝非法状态转换  │
├─────────────────────────────────────────────────────────┤
│  工具循环(第 05 期建的,复用)                           │
│  while True:                                             │
│    LLM → 决定调哪个工具、传什么参数                      │
│    代码 → 执行工具、把结果塞回 messages                  │
│    LLM → 看到结果,决定下一步                            │
│  特点:模型是"驾驶员",工具是"车",提示词是"交通规则"  │
└─────────────────────────────────────────────────────────┘
```

三层各司其职:

| 层 | 职责 | 能拦住什么 | 拦不住什么 |
|---|---|---|---|
| 提示词层 | 引导 LLM 该做什么 | 模型不知道该查 todo_list | 模型"假装"做完(自己编内容标完成) |
| 工具层 | 强制规则执行 | 跳过任务、并行多任务 | 模型编造任务内容 |
| 工具循环 | 驱动 LLM ↔ 工具交互 | — | — |

**关键洞察**:硬约束(工具层)能拦住"跳过"和"并行",但拦不住"模型自己编内容然后标完成"。这类行为只能靠提示词引导(软约束)。要硬拦,得在工具层加"需要用户确认才能标 completed"的逻辑,但那会复杂化本期教学目标。

### 为什么 Agent 需要 TodoList?

| 没有 TodoList | 有 TodoList |
|---|---|
| 模糊任务"一口气回答" | 先拆解再执行 |
| 不知道做到哪了 | 进度面板一目了然 |
| 多任务乱并行 | 单 in_progress 强制串行 |
| 无法回溯"做了什么" | 任务列表即执行日志 |

本质上,TodoList 是给 Agent 加了一个**外显的工作记忆**。第 07 期的 messages 是"对话记忆",TodoList 是"任务记忆"——它把"我要做什么、做到哪了"从模型的隐式上下文变成了显式数据结构。

### 一轮对话的完整流程

```
用户输入: "明天开会全体员工总结本周工作"
    │
    ▼
提示词层: todo_guide 说"列表为空时,判断是否复杂任务"
    │
    ▼
LLM 决策: "这是复杂任务,需要拆解"
    │
    ▼  todo_create(tasks=["收集要点", "整理议题", ...])
工具层: 创建 4 个 pending 任务,返回列表
    │
    ▼  结果塞回 messages
LLM 决策: "#1 设为 in_progress"
    │
    ▼  todo_update(1, "in_progress")
工具层: 双约束检查通过,状态更新
    │
    ▼  结果塞回 messages
LLM 回复: "#1 收集要点,请告诉我本周进展..."
    │  (提示词层:需要用户信息 → 停下,不要自己编)
    ▼
等待用户下一轮输入...
```

提示词引导行为 → 工具执行+约束 → 工具循环驱动交互。三层缺一不可。

### 两条约束的实现

```python
def todo_update(task_id: int, new_status: str) -> str:
    target = find_task(task_id)

    # 约束 1:顺序约束 —— 前面的任务必须全部完成才能开始
    if new_status == "in_progress":
        blocked_by = []
        for t in _todo_list:
            if t["id"] < task_id and t["status"] != "completed":
                blocked_by.append(t["id"])
        if blocked_by:
            return f"顺序约束:任务 #{task_id} 前面还有未完成任务 {blocked_by}"

    # 约束 2:单 in_progress —— 新 in_progress 时,把其他 in_progress 退回 pending
    if new_status == "in_progress":
        for t in _todo_list:
            if t["status"] == "in_progress" and t["id"] != task_id:
                t["status"] = "pending"  # 自动退回

    target["status"] = new_status
    return snapshot()
```

两条约束都是**工具层面强制执行**的,不是模型自觉遵守的:
- 约束 1:即使模型想跳过 #1 直接开 #3,工具会返回错误"前面还有未完成任务"
- 约束 2:即使模型尝试同时设两个 in_progress,第二个调用会把第一个自动退回 pending

### TodoList vs 人脑工作记忆

| 维度 | 人脑工作记忆 | Agent TodoList |
|---|---|---|
| 存储 | 前额叶皮层 | 内存 list[dict] |
| 容量 | 7±2 个组块 | 无限制(但建议 3-7) |
| 持久化 | 不持久,忘就忘了 | 会话级(重启清空) |
| 可视化 | 自己脑子里看不到 | 面板打印,用户也能看 |
| 约束 | 人也会多线程跑题 | 单 in_progress 强制串行 |

关键洞察:**TodoList 把"我要做什么"从隐式变显式**,从"模型脑子里"搬到"代码数据结构里"。这和第 07 期把"用户是谁"从 messages 搬到 USER.md 是同一个设计思路。

### TodoList 的状态转换图

```
     todo_create
         |
         v
     pending <───────┐
         |           │
    todo_update      │ (新 in_progress
     (in_progress)   │  自动退回)
         |           │
         v           │
    in_progress ─────┘
         |
    todo_update
     (completed)
         |
         v
    completed (终态)
```

状态转换是单向的:pending → in_progress → completed。虽然 `todo_update` 技术上支持从 completed 退回 pending,但工作指南引导模型走"单向流水线"。
