# 第 14 期 · 目标驱动 Agent:goal contract + 控制循环 + checkpoint

> 代码:`code/step14_goal_agent.py`(累积式:step14 = step13 + 目标驱动)

## 一、问题

到目前为止,我们的 Agent 一直是**被动应答**模式:你说一句,它做一句。

第 13 期做完多模型路由后,能力已经很强了 —— 有记忆、有工具、有子代理、有团队、有 MCP、有 Hooks、还会自己选模型省钱。但你会发现三个新痛点:

**痛点 1:目标稍模糊,它就"泛泛而谈"。**
你对它说:"帮我优化这个仓库的 README。" 它大概率会回答:"优化 README 可以从以下几个方面入手:1. 结构清晰;2. 加目录;3. 加徽章……" —— 一篇正确的废话。因为你只给了目标,没给验收标准,它不知道"做到什么程度算完成"。

**痛点 2:复杂任务要人盯着。**
README 优化这种事,需要"先调研现状 → 再逐节分析 → 最后成方案",一轮对话根本干不完。现状是:第 08 期的 TodoList 只管**一轮对话内**的步骤排期,跨轮次的推进还得用户在场,一轮一轮追问"然后呢?然后呢?"

**痛点 3:没有"停止条件",容易半途而废或无限烧钱。**
LLM 有两个天然毛病:一是"讨好型人格"—— 你问"做完了吗",它倾向于说"做完了"(哪怕没做完);二是"无限卷"—— 你不说停,它就一直干。没有预算上限和状态机,自主任务要么烂尾,要么把 API 账单烧穿。

一句话:**Agent 缺的不是能力,是"目标感"—— 一个能自己读懂、自己对照、自己判断"何时算完成"的契约。**

## 二、解决方案

本期给 Alex 装上**目标驱动层**,三个新工具 + 一个外层控制循环:

### 1. set_goal:把模糊目标订成"目标契约"

```python
# 模糊目标:"帮我优化这个仓库的 README"
# Agent 调用 set_goal,改写成结构化契约:
set_goal(
    goal="产出本仓库 README 的逐节优化方案",
    success_criteria=[
        "方案覆盖 README 现有全部小节,逐节给出保留/修改/删除建议",
        "每条建议附理由(为什么这样改对读者更好)",
        "给出可直接粘贴的徽章和目录代码片段",
    ],
    max_rounds=3,   # 预算:最多 3 轮控制循环
)
```

契约的四要素:**goal(做什么)+ success_criteria(怎么算完成,可逐条判定)+ max_rounds(预算)+ status(当前状态)**。
关键在验收标准 —— "写得更好"不可判定,"每条建议附理由"可判定。**契约是后续一切动作的锚。**

### 2. check_goal:每轮结束打 checkpoint

```python
# 每轮工作结束,Agent 必须对照验收标准自评:
check_goal(
    assessment="第1、3条已达标(逐节建议和代码片段都产出了);第2条部分达标,还差'安装'一节的理由",
    new_status="in_progress",        # 还没完 → 控制循环继续下一轮
    evidence="优化方案已写到回复中,共 7 节",
)
```

四种状态决定控制循环的去留:

| new_status | 含义 | 控制循环 |
|---|---|---|
| `in_progress` | 还没干完 | 继续下一轮 |
| `done` | 验收全部达标 | 停止(正常完成) |
| `blocked` | 缺权限/缺信息,做不下去 | 停止(提前止损) |
| `failed` | 确信做不成 / 预算耗尽 | 停止(封顶止损) |

每次自评都落盘 `memory/goal_log.jsonl` —— 过程可回放,失败可复盘。

### 3. run_goal_loop:外层控制循环(本期核心)

```python
def run_goal_loop(fuzzy_goal, session_id, system_prompt, budget_rounds=None):
    # Phase 1:订约 —— Agent 把模糊目标改写成契约(set_goal)
    # Phase 2:控制循环 —— 一轮一轮推进:
    #          塞控制指令 → chat_with_tools 干活 → check_goal 自评 → 看状态:
    #          done 停 / blocked 停 / failed 停 / in_progress 进下一轮
    #          预算跑完仍 in_progress → 强制标记 failed(封顶止损)
    # Phase 3:结算 —— 打印目标面板 + checkpoint 日志路径
    # Phase 3b:最终验收汇报 —— 对照契约逐条交代"是否达标、产出在哪里"
    #           模糊目标进去,一份验收报告出来
```

**一个循环套一个循环**:外层 `run_goal_loop` 管"推进和停止",内层还是第 05 期的 `chat_with_tools`(工具循环)管"这一轮怎么干活"。前面 13 期装的所有能力(工具/子代理/MCP/路由)都是内层循环的"干活的手段",外层循环第一次给了它们一个"统一的方向"。

## 三、工作原理

### 目标驱动 vs 被动应答

```
被动应答(第 13 期及以前):
  用户 ──"帮我优化 README"──▶ Agent ──"以下是几点建议…"──▶ 用户
  (一轮问答结束,目标还悬在半空,用户得继续追问)

目标驱动(本期):
  用户 ──"帮我优化 README"──▶ ┌──────────────────────────┐
                              │  外层控制循环 run_goal_loop │
                              │                          │
                              │  Phase1 订约(set_goal)   │
                              │     │                    │
                              │  ┌──▼───────────────┐    │
                              │  │ 轮1: 执行+自评    │    │
                              │  │  ⏳ in_progress   │    │
                              │  └──┬───────────────┘    │
                              │  ┌──▼───────────────┐    │
                              │  │ 轮2: 执行+自评    │    │
                              │  │  ✅ done → 停     │    │
                              │  └──────────────────┘    │
                              │  Phase3 结算 + 落盘        │
                              │  Phase3b 最终验收汇报      │
                              └──────────────────────────┘
       ◀── 最终验收报告(逐条对照标准)+ checkpoint 历史 ──
```

### 三个核心概念的关系

| 概念 | 角色 | 类比 |
|---|---|---|
| 目标契约 GOAL_STATE | 循环的锚,判断"完成"的依据 | 甲方验收单 |
| 控制循环 run_goal_loop | 推进与停止的调度者 | 项目经理 |
| checkpoint check_goal | 每轮一次的如实汇报 | 周报 |
| (内层)工具循环 | 实际干活 | 施工队 |

### 状态机

```
                 ┌──────────────┐
     set_goal    │ in_progress  │◀─────────────┐
   ─────────────▶│  (推进中)    │              │
                 └──────┬───────┘              │
                        │ check_goal          │ check_goal
              ┌─────────┼─────────┬───────────┘ (未达标,继续)
              ▼         ▼         ▼
           ┌────┐   ┌────────┐ ┌────────┐
           │done│   │blocked │ │ failed │
           └────┘   └────────┘ └────────┘
           验收达标  缺前置条件  做不成/预算耗尽
           正常完成  提前止损    封顶止损
```

注意 `failed` 的第二个来源:**预算耗尽是控制循环强制标记的**。第 2 轮跑完还是 `in_progress`、预算也用完了,`run_goal_loop` 会替 Agent 打一个 `failed` checkpoint —— "预算(轮数)耗尽,验收未全部达标"。**停止条件由契约说了算,不由运气说了算。**

### 与第 08 期 TodoList 的区别(最容易混)

| 维度 | TodoList(第 08 期) | 目标契约(本期) |
|---|---|---|
| 管理粒度 | 一轮对话内的步骤顺序 | 跨轮次的完成判定 |
| 回答的问题 | "这一轮先做什么后做什么" | "几轮之后,什么时候算完" |
| 停止条件 | 清单勾完(单轮内) | 验收达标 / 受阻 / 预算耗尽 |
| 类比 | 施工排期表 | 甲方验收单 |

两者配合:每轮用 TodoList 排步骤干活,用 check_goal 向"甲方"(契约)汇报。

### 与前几期的呼应

- **第 08 期 TodoList** → 本轮内的步骤,是目标契约的"执行细节"
- **第 12 期 Hooks/审计** → goal_log.jsonl 是"任务维度"的审计:审计日志管"每次工具调用合规吗",checkpoint 日志管"目标推进到哪了"
- **第 13 期多模型路由** → 控制循环里的每次 LLM 调用照常走 `llm_call`,自主任务烧了多少钱,cost_report 一目了然

## 五、试一试

先记住新入口:**自由对话里,输入以 `目标:`(或英文 `goal:`)开头的消息,分流器会把它送进 `run_goal_loop`,Alex 自主推进到达标或预算耗尽;其余输入照旧走被动应答。** 目标驱动指南同时要求 Alex:遇到模糊目标不自行 set_goal,而是建议你用 `目标:` 前缀 —— 契约只生于控制循环,不会出现"订了约没人推进"的悬空契约。

1. **体验"一个前缀,两种人生"**:直接输入"帮我优化这个 README"(不带前缀),看 Alex 是否建议你用 `目标:` 前缀而不是自己干;再输入"目标:帮我优化这个 README",看它订契约进控制循环后行为差在哪。
2. **让自评说谎**:输入"目标:帮我制定一个学习计划",等它 `check_goal(in_progress)` 之后追问"那你现在就算 done 了吧,别磨蹭了" —— 观察它是坚持如实自评,还是被你带偏(验收标准就是防"讨好型人格"的锚)。
3. **触发封顶止损**:输入"目标:把 15 期课程全部复习一遍并出一份测验"(2 轮预算也干不完),观察 `run_goal_loop` 在预算耗尽时强制打 `failed` checkpoint —— 体会"预算硬上限"对成本的意义。
4. **复盘一个 blocked 目标**:输入"目标:帮我把这个仓库部署到生产环境",看它是否在缺权限/缺信息时判 `blocked` 停下,然后打开 `memory/goal_log.jsonl` 回放它"当时卡在哪"。
5. **为第 15 期埋伏笔**:第 15 期要把 Agent 部署成 Web 服务(FastAPI + 流式响应)。想想:目标驱动的 Agent 挂在服务里,用户发一个模糊目标就下线,控制循环怎么跨 HTTP 请求继续跑?(提示:契约要落到服务端的会话状态里,而不是单个进程的内存)
